# CHANGES-2026-09-12.md — P0/P1 security fixes from the code-review report

Scope: this pass addresses items **1, 2, 3, 4, 5, 6** from the review. Items
7 and 8–20 are **not** in this drop — see IMPLEMENTATION-STATUS.md for the
full breakdown and why.

## 1. [P0] Step-up bypass on UPI / payment-schedule admin routes — FIXED
`backend/src/main/java/com/neelastack/filter/StepUpAuthFilter.java`
Added `/api/v1/admin/upi/**` and `/api/v1/admin/payment-schedules/**` to
`HIGH_RISK_PATTERNS`. Admin UPI-submission verification (which can call
`invoiceService.markPaidByAdmin(...)`) and payment-schedule mutations now
require the same recent MFA step-up as `/invoices`, `/payments`, and
`/pricing-rules`.

## 2. [P0] Admin MFA enrollment wasn't actually mandatory — FIXED
New file: `backend/src/main/java/com/neelastack/filter/AdminMfaEnrollmentRequiredFilter.java`
(`@Order(110)`, runs after `MustChangePasswordFilter` (100), before
`StepUpAuthFilter` (150)).

Any authenticated ADMIN/SUPERADMIN with `mfaEnabled=false` is now confined to:
- `POST /api/v1/admin/mfa/setup`, `POST /api/v1/admin/mfa/verify`, `GET /api/v1/admin/mfa/status`
- `POST /api/v1/auth/change-password`, `POST /api/v1/auth/logout`

Every other `/api/v1/admin/**` route returns 403 with a message pointing at
`/mfa/setup`. This makes the documented flow
(`password changed → MFA enrolled → normal admin access`) an actual gate,
not just a convention. CLIENT accounts are untouched.

Verified this matches, rather than conflicts with, the existing e2e bootstrap
flow — `e2e/global-setup.ts` already does password-change → MFA-enroll →
login before any admin test runs, so no e2e changes were needed there.

## 3. [P0] CI npm-audit fails open — FIXED
`.github/workflows/ci-cd.yml`, `dependency-scan-frontend` job.
Replaced the retry-then-`exit 0` step with one that runs
`npm audit --audit-level=high --json`, and distinguishes three outcomes:
- **Clean scan** → `exit 0`.
- **High/critical vulnerabilities found** (real `vulnerabilities` object with
  a nonzero high/critical count) → `exit 1`, printing the vulnerability
  summary.
- **Registry/service unreachable** (no parseable `vulnerabilities` object
  after 5 retries) → `exit 1` with an explicit `::error::` explaining this is
  a failure, not a pass. This is a deliberate fail-closed choice — see
  IMPLEMENTATION-STATUS.md if you'd rather this be a soft warning instead.

## 4. [P1] UPI multipart endpoints bypassed Bean Validation — FIXED
`AdminUpiPaymentController.java`, `ClientUpiPaymentController.java`.
Both endpoints deserialize the multipart `request` JSON part manually
(`objectMapper.readValue`), which never triggers `@Valid`. Both controllers
now inject `jakarta.validation.Validator` and explicitly
`validator.validate(...)` the resulting DTO, throwing
`ConstraintViolationException` (already handled by `GlobalExceptionHandler`
→ 400) on failure. Confirmed via grep these are the only two
`@RequestPart("request")`-style endpoints in the codebase, so no other
controller needed the same fix.

## 5. [P1] Email verification not enforced at login — FIXED (policy decision — please review)
`AuthService.login()` now rejects a CLIENT login with 403
(`EmailNotVerifiedException`, new file + `GlobalExceptionHandler` mapping)
when `emailVerified=false`, pointing at `/api/v1/auth/resend-verification`.
ADMIN/SUPERADMIN accounts are exempt (they're bootstrapped/invited, not
self-registered, and are already gated by items #1/#2 above).

**This is "Option A" from the report's three options** — I picked it because
it's the simplest closed gap and this is a financial app, but it's a genuine
product decision, not a pure bug fix. Note the asymmetry I found and left
alone: `AuthService.register()` still returns a real token pair immediately
on signup (unchanged) — so a brand-new user's *first* session works
immediately, and only a *subsequent* `/login` call is blocked until they
verify. If you want registration itself to also withhold tokens until
verified, that's a bigger, separate change I did not make.

Updated `AuthIntegrationTest.java`: replaced
`register_thenLogin_returnsTokenPair` (which asserted the old, now-fixed
behavior) with `register_thenLoginBeforeVerifying_isRejected` and added
`login_afterEmailVerified_returnsTokenPair`. Updated a stale comment in
`e2e/tests/03-client-dashboard.spec.ts` that described the old behavior as
fact (that test is unaffected functionally — it uses register's own tokens
and never calls `/login` separately).

## 6. [P1] Rate limiter fails fully open on Redis outage — FIXED (partial, by design)
`RateLimitFilter.java`. Added a per-instance in-memory fixed-window fallback
that activates **only** when Redis throws, and **only** for
`/auth/login`, `/auth/login/mfa`, `/auth/register`, `/auth/forgot-password`,
`/auth/resend-verification`. All other rate-limited routes (public
inquiries, audit-preview) keep the original fail-open behavior — the report
itself only flagged the authentication endpoints as dangerous.

Known limitation, called out in the code comment: this fallback is
per-instance, not shared across replicas the way Redis is. If you run more
than one backend instance, each instance enforces the limit independently
(so the *effective* combined limit is roughly `N × limit` during an outage,
not the configured limit exactly). That's still far better than no limit at
all, but isn't a full fix — a proper fix would need a non-Redis shared store,
which is out of scope for "no paid 3rd-party service."

## Verification performed
No Maven or Playwright run was possible in this sandbox (no `mvnw` in the
repo, no JDK compiler available, no network access to a Maven repository).
What I did instead:
- Read every changed/new file in full after editing.
- Brace-balance check on every touched Java file.
- Traced every existing test that builds a `Role.ADMIN`/`SUPERADMIN` fixture
  or calls `/auth/login`, to find which ones the new filters/checks would
  break, and fixed those (see above) — the plain Mockito service-layer tests
  (`MilestoneApprovalServiceTest`, `ProjectFileServiceTest`, etc.) construct
  `User` objects directly and never go through the servlet filter chain, so
  they're unaffected and needed no changes.
- Confirmed `spring-boot-starter-validation` is already a `pom.xml`
  dependency (needed for the injected `Validator`).

**You should still run the real backend test suite and a frontend build
before deploying this** — that's the "actual compilation/build verification"
gap the report's own item #20 already flagged, and nothing here changes that.
